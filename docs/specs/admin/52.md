Filters (ინტერესი, მდებარეობა) are rendered as plain text lines, not controls: implement as two select filters (interest from `interests.chipKa`, city from distinct `users.city`) - proposal, the design shows only the selected values. Result rows are plain text, not links (a creator profile screen is not in this set).

## Data mapping
- Creator row: `SELECT u.name, i.nameKa/chipKa, COUNT(s.id) FILTER (WHERE s.status='approved') FROM users u JOIN user_interests ui ... JOIN interests i ... LEFT JOIN submissions s ON s.user_id=u.id WHERE u.deleted_at IS NULL AND <opt-in> AND i.id=:interest AND u.city=:city GROUP BY u.id`. Interest label per row = user's interest (row 2 shows "ცხოვრების სტილი" although filter is "კულინარია": a user can have several interests; define which is displayed).
- `დამტკიცებული ნამუშევარი` count = approved submissions (`submissions.status='approved'`).
- **NO DATA SOURCE (blocking)**: the discoverability opt-in ("ძიებაში გამოჩენა თავად დაუშვეს") and the "საჯარო პროფილი" (public profile) flag. `users` has no such column (only name, bio, city, avatarUrl, ...). Need a new boolean (e.g. `users.discoverable` / `profile_public`, default false) with a user-facing consent toggle; until it exists the list must be empty/"unavailable", not filled with all users (privacy requirement stated in the copy).
- Also no source: follower counts, reach, engagement, age/gender (not shown on this frame). Names in the mock are placeholders ("ნინო ბერიძე", "სალომე მჭედლიშვილი"): do not hardcode.
